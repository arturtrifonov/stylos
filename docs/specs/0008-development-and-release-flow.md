# SPEC 0008 — Development and release flow

**Status:** Open — written 2026-09-06
**Date:** 2026-09-06

A work order. `0.1.0` is tagged and the project now has a second version ahead of it, but no flow: no rule for when a release happens, no gate on a pull request, and nothing stopping an agent — or a hand — committing to `master`. On 2026-09-05 an agent's command fast-forward-merged a branch into `master` because there was nothing to refuse it, and the `add-tokens` branch carries a finished CSS build against an `ARCHITECTURE.md` that still says the build does not exist. Both are the same absence.

This spec builds the flow. The rules it establishes are normative in [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §7; the files here implement them. No change to any component, token or contract.

---

## 1. What a release is

**A pull request is not a release.** A release is a decision, taken when one of these holds:

- a stage gate in [`PLAN.md`](../../PLAN.md) §1 is met (`0.2.0` when S5's gate passes, `0.3.0` when S6's does); or
- one of the three versioned things — a registry contract's `api`, the `tokens/` set, or the published Figma library ([`ARCHITECTURE.md`](../../ARCHITECTURE.md) §9) — changed in a way that has to be named and handed to a consumer.

Everything else accumulates. Document edits, tooling, plan changes, the CSS build, a foundation clarification — none of them is a release, and none bumps a version. They land in `master` through pull requests and wait under `## [Unreleased]` in [`CHANGELOG.md`](../../CHANGELOG.md) until a release carries them out.

So the CSS build on `add-tokens` is not `0.1.1`. It is Stage 5 work; it changes nothing the version covers; it ships inside `0.2.0`.

**One version line, in lockstep.** `@stylos/ui` and the system share one number until `1.0`: the package's `0.2.0` implements the system's `0.2.0`. [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §9 currently gives the package its own semver — that paragraph is amended to lockstep, and the separate-schedule rule returns as an option to revisit at `1.0`.

## 2. How work reaches master

`master` is the release line. Nothing is committed to it directly and nothing is merged into it locally.

1. Branch from `master`.
2. Open a pull request with `gh pr create`.
3. CI (§4) must be green.
4. Squash-merge on GitHub. The PR title is the squash commit subject, in the imperative; the PR body holds the `CHANGELOG.md` lines the change earns.
5. The head branch is deleted (GitHub's *Automatically delete head branches* is on).

Several pull requests may compose one release. A release is cut when §1 says so, not when a PR merges.

## 3. Definition of done for a pull request

A PR is ready to merge when:

- `npm test`, `npm run validate:registry`, `npm run validate:skills` and `npm run tokens:check` all pass;
- **every document describing a capability the PR changes is corrected in the same PR.** A change to how the system is built touches [`ARCHITECTURE.md`](../../ARCHITECTURE.md); a change to sequence touches [`PLAN.md`](../../PLAN.md); a finished spec's row moves to *Built* in [`docs/specs/README.md`](README.md). The `add-tokens` state — a built feature against documents that deny it — is the failure this line exists to prevent;
- a `## [Unreleased]` line is added when the change is worth a release note;
- generated output is not hand-edited: `build/`, `packages/*/dist/`, `tokens/*.yaml` (generated by import) and `skills/dist/` change only by rebuilding their source.

This list is the pull-request template (§5.4).

## 4. Continuous integration

`.github/workflows/ci.yml`, on `pull_request` and on `push` to `master`.

- Node 22 (the version `--test` and the tools are written against). No dependencies today, so no `npm ci` step until `packages/ui` has a lockfile; add it in the same PR that adds the package.
- Steps: `npm test`, `npm run validate:registry`, `npm run validate:skills`, `npm run tokens:check`, then `npm run tokens:css` and `npm run build` to prove the generators run.
- The job is the required status check on the branch **once the repository can enforce one** (§6). Until then it is advisory, and the local hooks (§5.2) are the enforcement.

When `packages/ui` lands, the workflow gains its build, its component tests (Vitest browser mode, Playwright), axe on every story ([`accessibility.md`](../foundations/accessibility.md)) and Stylelint — added by [SPEC 0009](0009-stylos-ui-package.md), not here.

## 5. The files

### 5.1 `CLAUDE.md` at the repository root

There is none today, which is why an agent had no rule to break. Under 200 lines, and it states:

- **This session is decisions, specs, architecture, review. Implementation is done in Claude Code, in a branch.** (The standing division of labour.)
- **Never commit to `master`, never `git merge`, never `git tag`, never push to `master`.** Work goes to a branch and `gh pr create`; releases are a person's act.
- The definition of done (§3), so a change and its documents move together.
- Run the four checks before opening a PR.
- Generated output is rebuilt, never edited.
- The Svelte tooling for implementation work: the `sveltejs/ai-tools` plugin and its autofixer ([SPEC 0009](0009-stylos-ui-package.md)).

`CLAUDE.md` is guidance the model follows, not a control that binds it — §5.2 and §5.3 are the controls.

### 5.2 Git hooks — `.githooks/`, enabled by `git config core.hooksPath .githooks`

The one guard that binds a hand as well as an agent, and the only one that works on this repository today (§6).

- `pre-commit` refuses a commit whose current branch is `master`.
- `pre-push` refuses a push to `refs/heads/master` unless `STYLOS_RELEASE=1` is set — the release ritual (§7) sets it, ordinary work never does.

One-time `git config core.hooksPath .githooks` per clone; the command and the reason go in the README's *Working on it* section, since a hook path is not configured by cloning.

### 5.3 `.claude/settings.json` — committed, shared

`.claude/settings.local.json` today holds only personal allow rules and is git-ignored. The shared file carries the guards, so every session in the repository gets them:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "deny": [
      "Bash(git merge:*)",
      "Bash(git tag:*)",
      "Bash(git push --force:*)",
      "Bash(git push -f:*)",
      "Bash(git reset --hard:*)",
      "Bash(git checkout master)",
      "Bash(git switch master)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Bash(gh pr merge:*)"
    ]
  }
}
```

A `deny` rule is refused even inside a compound command — `x && git merge y` is caught — and a `deny` outranks any `allow` ([Claude Code permissions](https://code.claude.com/docs/en/permissions)). `git merge` is denied outright because there is no local merge in this flow at all; the release ritual tags from the CLI with `STYLOS_RELEASE=1`, which the git hook gates rather than the settings file. This is defence in depth, not the boundary — the git hook is.

### 5.4 `.github/pull_request_template.md`

The definition of done (§3) as a checklist, so a PR shows what it must satisfy.

### 5.5 `CHANGELOG.md`

Gains a `## [Unreleased]` section immediately, above `## [0.1.0]`. Its first entry is the CSS build (SPEC 0007) — the work that is on a branch now with nowhere to be recorded.

## 6. Repository visibility

Branch protection rules and rulesets are not enforced on a private repository on GitHub Free — confirmed for 2026 ([community #190190](https://github.com/orgs/community/discussions/190190), and [the docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)). So on the repository as it stands, the CI check cannot be made *required* and `master` cannot be protected on the server; the git hook (§5.2) is the only enforcement, and it binds this machine only.

**Decision (2026-09-06): make the repository public.** Public repositories get branch protection and required status checks on Free. Public is not a licence — the repository stays `UNLICENSED` until the licence question is taken ([`PLAN.md`](../../PLAN.md) §6, an `alpha` question), and `UNLICENSED` on a public repository means visible, not reusable. Once public:

- protect `master`: require the CI check, require a pull request, disallow force-push and deletion;
- the git hook and the settings file stay as the local layer, so a mistake is caught before it reaches the server too.

## 7. The release ritual

When §1 says a release is due, in a `release/x.y.z` branch and PR:

1. `CHANGELOG.md`: `## [Unreleased]` becomes `## [x.y.z] — <date>`, keeping its dated subheadings; add `### Figma library` if the library moved.
2. `package.json` version to `x.y.z`.
3. README status line.
4. If the Figma library republishes: set `meta/version` in *Stylos / Styles*, `npm run tokens:import -- --collection meta`, confirm `figma/library.yaml` and `npm run tokens:check`.
5. Merge the release PR (squash).
6. On `master`, with the ritual's `STYLOS_RELEASE=1`: annotated tag `vX.Y.Z`, then `git push origin vX.Y.Z` (a plain push does not send tags).
7. GitHub release from the tag, body copied from the `CHANGELOG.md` section.
8. Publish the Figma library **after** the tag, description pointing at the release — the order fixed in [SPEC 0006](0006-versioning-and-release-0-1-0.md) §9 E.

## 8. Acceptance criteria

- A commit to `master` is refused locally; a push to `master` without `STYLOS_RELEASE=1` is refused.
- `git merge`, `git tag` and force-push are denied in a Claude Code session; `git push` and `gh pr merge` prompt.
- `CLAUDE.md` exists at the root and states the branch-and-PR flow and the definition of done.
- CI runs the four checks plus the two builds on every pull request.
- `CHANGELOG.md` has a `## [Unreleased]` section, and the SPEC 0007 CSS build is recorded in it.
- [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §7 states: master is the release line reached only by PR; a PR is not a release; the definition of done; and the lockstep version rule (§9 amended).
- The repository is public, `master` is protected, and the CI check is required.
